# YouTube VoT — обход блокировок (ветка `bypass`)

Без root приложение использует `VpnService`, чтобы перехватывать только трафик WebView-провайдера. Целевой путь обхода:

```text
WebView provider -> Android TUN -> hev-socks5-tunnel -> ByeDPI SOCKS5 -> сеть
```

Обычный `Service` не может изменить сетевой маршрут приложения без root; `VpnService` нужен именно как способ получить TUN file descriptor.

## Компоненты

- `src/java/com/vot/youtube/BypassVpnService.java` — lifecycle VPN, TUN и запуск транспорта.
- `src/java/com/vot/youtube/ByeDpiNative.java` — JNI-обёртка локального SOCKS5-прокси.
- `src/java/hev/htproxy/TProxyService.java` — JNI-обёртка `hev-socks5-tunnel`.
- `src/cpp/byedpi` — pinned submodule с ByeDPI C core.
- `src/cpp/hev-socks5-tunnel` — pinned submodule с tun2socks и его Android build files.
- `src/java/com/vot/youtube/BypassStrategy.java` — каталог стратегий десинка (аргументы byedpi).
- `src/java/com/vot/youtube/BypassProbe.java` — батарея замеров, пороги, модель результата.
- `src/java/com/vot/youtube/BypassProbeService.java` — изолированный процесс, который меряет.
- `BYPASS.md` не заменяет проверку на устройстве: после изменения нативного транспорта нужно проверить загрузку YouTube, TLS и остановку VPN.

## Измерение обхода

Обход нельзя измерить из процесса приложения: пакет исключён из туннеля через
`addDisallowedApplication("com.vot.youtube")`, поэтому его сокеты всегда идут
напрямую мимо десканка и всегда выглядят рабочими. Меряет отдельный сервис
`BypassProbeService` с `android:isolatedProcess="true"`: у изолированного
сервиса собственный динамический UID, в disallowlist он не значится и потому
идёт через туннель.

**Это самое рискованное место конструкции.** Вывод опирается на то, что
`addDisallowedApplication` исключает UID пакета, а не все UID пакета. Проверка
на устройстве обязательна до того, как вердиктам можно доверять.

Батарея — четыре стабильных хоста (`www.youtube.com`,
`youtubei.googleapis.com`, `i.ytimg.com`, `redirector.googlevideo.com`): TCP,
TLS-хендшейк и HTTP-ответ одним замером. Один хост не годится — API и
видео-CDN в РФ режутся по-разному, и проверка одного даёт ложный вердикт.
Хосты намеренно покрываются `BYPASS_HOSTS`: byedpi сопоставляет по суффиксу с
точкой (`host_cmp` в `mpool.c`).

Пороги в `BypassProbe` **не откалиброваны**: осмысленные значения дают только
замеры в заблокированных сетях. `HARD_TIMEOUT_MS` — за этой границей стратегия
упала; `SOFT_NORM_MS` — прошла, но это последний выбор, а не первый. Причина
двух порогов: РКН обычно душит, а не блокирует, и «зелёная» стратегия с
четырёхсекундным хендшейком дала бы зелёную галочку и тормозящее видео.

Порядок работы при старте:

1. **быстрый замер** текущей стратегии, без повторов — на большинстве сетей он
   проходит, и полный перебор там был бы налогом на батарею и трафик;
2. **лестница** — две дешёвые проверки: прошлый победитель и стратегия по
   умолчанию;
3. **перебор** всех стратегий каталога, только если остывание истекло.

Побеждает наименьшая медиана по худшему хосту; при равенстве — наименее
агрессивная стратегия (считаются обе формы флагов, короткие и длинные).
Текущая стратегия уходит только при значимом выигрыше, иначе приложение
скачет между стратегиями на шумных замерах.

Остывание действует **только на перебор**: право сказать «не работает» даёт
именно он, и запрещать его нельзя — иначе приложение начнёт врать в другую
сторону. Быстрый замер и шаги лестницы не остывают никогда.

## Транспорт: что поменялось и почему

- **DNS не задаётся** (`addDnsServer` убран). Телефон использует DNS своей сети.
  Раньше стоял `1.1.1.1`, из-за чего весь телефон резолвил через Cloudflare, и
  недоступность этого резолвера ломала сеть у всех приложений. Петли DNS не
  было и нет: процесс приложения исключён из туннеля.
- **UDP выключен** в конфиге транспорта (`udp: 'off'`) и добавлен `--no-udp` в
  byedpi. Стратегии не десканкают QUIC (`--auto=torst` работает только по TLS),
  а YouTube в WebView сначала идёт по QUIC. В конфиге транспорта UDP включается
  **только** при значении ровно `'udp'` (`hev-config.c`: `strcasecmp(udpm,
  "udp")`), любое другое оставляет `srv.udp_in_udp = 0`.
- **IPv6 заведён в туннель** (`fd00:9::2` + маршрут `::/0`). Раньше IPv6 уходил
  напрямую мимо десканка, и приложение врало о покрытии трафика. Вердикт по
  IPv6 подтверждается замером, иначе приложение честно откатывается.
- **MTU 1400** по умолчанию, настраивается. 1500 — источник плавающих подвисаний
  на сетях с PPPoE и туннелями операторов.

Маршрут `0.0.0.0/0` остаётся широким — это осознанная цена: per-app не работает
для изолированного процесса WebView, а адреса CDN меняются.

Подмена стратегии на лету не трогает транспорт: список доменов не зависит от
стратегии, поэтому чужой трафик через прокси идёт как раньше.

## Стратегии десинка
Стратегия — это набор CLI-флагов byedpi (`-s` сплиты, `-d` disorder, `-f` fake
TLS, `-A` авто-режим, `--ttl`, `-Mh`), а не отдельная реализация обхода.
Наборы взяты из публичного каталога byedpi-стратегий, который использует
приложение zaprett (`CherretGit/zaprett-repo`, `index.json`, тип `byedpi`).

Код zaprett (GPL-3.0) не используется: перенесены только строки аргументов.
Сами примитивы `hev-socks5-tunnel` и `byedpi` — MIT, поэтому новой лицензии
на проект не возникает.

Настоящий zapret (`bol-van/zapret`, механизм `nfqws`) на Android без root
не запускается: ему нужен `netfilter_queue` и root. Порт
`egor-white/zaprett` существует только как Magisk-модуль, и его README прямо
отправляет rootless-режим в отдельное приложение. Поэтому наш rootless-обход —
это ровно то, что zaprett делает без root: `VpnService` + `hev-socks5-tunnel` +
byedpi, а стратегии — способы рассинхронизации.

Правила каталога:

- список доменов задаёт только приложение (`BypassVpnService.BYPASS_HOSTS`) и
  передаётся первым: byedpi обрабатывает только первое вхождение `-H`
  (`main.c`: `if (dp->file_ptr) continue;`). Списки внутри стратегии
  вырезаются, чтобы не сузить YouTube-профиль;
- базовый `--timeout` добавляется, только если стратегия не задала свой
  (`-t`/`--timeout`);
- `--no-udp` добавляется всегда, если стратегия не выразила запрет сама
  (`-U`/`--no-udp`);
- стратегия по умолчанию `default` сохраняет поведение v2.5.5.

Значение в `bypass_prefs` под ключом `strategy` — это **гипотеза, а не
настройка**: она записывается при каждом успешном замере и всегда
перепроверяется быстрым замером. Ручной выбор в настройках лишь задаёт
гипотезу, он не отменяет измерение. Аргументы byedpi читаются один раз при
старте прокси, поэтому смена гипотезы и MTU перезапускает обход.

## Сборка

- Инициализировать submodules: `git submodule update --init --recursive`.
- Установить Android NDK и задать `ANDROID_NDK_ROOT` либо использовать `$ANDROID_SDK_ROOT\ndk\<version>`.
- Запустить из корня: `powershell -ExecutionPolicy Bypass -File .\\build.ps1`.
- `build.ps1` собирает native-библиотеки, затем выполняет `aapt2 -> javac -> d8 -> ZipFix -> zipalign -> apksigner`.
- `tools/ZipFix.java` нормализует ZIP entries и добавляет native-библиотеки как `lib/<abi>/*.so`. Префикс `lib/` добавляется только если его ещё нет: `ndk-build` при `NDK_LIBS_OUT=<dir>` уже раскладывает библиотеки в `<dir>/lib/<abi>/`, и повторный префикс дал бы `lib/lib/<abi>/...`.
- `build.ps1` перекомпилирует `ZipFix` на каждой сборке: каталог `build/` переживает сборки, поэтому наличие `ZipFix.class` не означает, что он собран из текущего `tools/ZipFix.java`.

### Контракт JNI (нарушение = падение при включении обхода)

`hev-socks5-tunnel` регистрирует нативные методы в `JNI_OnLoad` и ищет класс
`hev/htproxy/TProxyService`. Если класс не найден или сигнатуры не совпадают,
`RegisterNatives` получает `java_class == null` и **убивает процесс** с
«JNI DETECTED ERROR IN APPLICATION: java_class == null».

Что должно выполняться в `TProxyService.java`:

- пакет `hev.htproxy`, имя класса `TProxyService`;
- `TProxyStartService(String, int)` возвращает `void` (сигнатура `(Ljava/lang/String;I)V`), **не** `boolean`;
- `TProxyStopService()` — `void`;
- `TProxyGetStats()` — `long[]`;
- метода `TProxyIsRunning` в нативной таблице нет, вызывать его нельзя.

Сабмодуль `src/cpp/hev-socks5-tunnel` запинен и не модифицируется: контракт
соблюдается на стороне Java.

### Обязательная проверка результата сборки

Транспорт состоит из **двух** нативных библиотек. Без `libhev-socks5-tunnel.so`
`BypassVpnService.isReady()` возвращает false и переключатель обхода отвечает
«движок обхода не готов», хотя APK собирается, подписывается и ставится без
ошибок. Поэтому после сборки проверяйте, что в APK лежат 8 библиотек:

```
unzip -l out/YouTubeVot.apk | grep '\.so$'
# по две на каждую ABI:
#   lib/<abi>/libbyedpi.so
#   lib/<abi>/libhev-socks5-tunnel.so
```

Собирать оба модуля обязан `src/cpp/Android.mk`: он подключает
`hev-socks5-tunnel/Android.mk` из сабмодуля.

## Важные ограничения

- Текущий bypass не должен захватывать собственный UDP/TCP трафик приложения: процесс `com.vot.youtube` исключается из TUN, иначе локальный SOCKS5-прокси зациклится сам на себя.
- Allowlist по пакетам не работает и использоваться не должен: изолированный процесс WebView (`com.google.android.webview:sandboxed_process0`) имеет собственный UID и в allowlist не попадает, поэтому трафик YouTube уходит мимо туннеля. Вместо этого из VPN исключается только собственное приложение (`BypassVpnService.DISALLOWED_PKGS`).
- Старые `BypassEngine`, `TcpFlow` и `BypassProto` оставлены как legacy-протокольный код и не являются рабочим транспортом приложения.
- Статус проверки на реальном заблокированном домене должен подтверждаться на устройстве; статическая проверка нативных символов и протоколов не заменяет сетевой тест.
