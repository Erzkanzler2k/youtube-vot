# YouTube VoT — обход блокировок (ветка `bypass`)

Отдельная ветка для обхода блокировок РКН **без root** через встроенный
VPN-сервис Android (`VpnService`). В `main` этот код не попадает.

---

## Архитектура

```
VpnService (TUN-устройство) → BypassEngine (обработка пакетов) → "наружу"
                                          │
                                    Socket + protect()
                                    (сеть не "ходит" через VPN)
```

**Компоненты**

- `BypassVpnService.java` — `VpnService`:
  запрос разрешения у пользователя → `startForeground` (обязательно на API 26+)
  → поднятие TUN через `Builder` (адреса, маршруты, DNS) → передача
  файлового дескриптора движку. В TUN попадает **только** трафик нашего
  приложения и WebView-провайдеров — остальные приложения исключены
  (`addDisallowedApplication`), интернет остальных не ломается.
- `BypassEngine.java` — движок обхода: читает пакеты из TUN, разбирает
  IPv4/TCP/UDP, применяет DPI-обход, исходящие соединения открывает через
  `Socket` с `protect()`.
- `TcpFlow.java` — состояние одного TCP-соединения: mini-TCP перед
  приложением (свой SYN+ACK с нашим ISN, сплайсинг seq/ack), пересылка
  данных наружу, SNI-перехват и фрагментация ClientHello.
- `BypassProto.java` — чистая протокольная логика (парсинг IPv4/TCP/UDP,
  checksum, SNI из TLS ClientHello, суффиксные матчи); проверена
  десктоп-тестом `tools/ProtoTest.java` (27/27).

**Ключевой предохранитель:** если TUN закрылся или запись в него падает —
движок сам останавливает сервис (`onStop` → `stopSelf`), VPN снимается.
Недоработанный перехват не должен отрубать интернет.

## Статус

### Этап 1 — инфраструктура (готово)

- [x] `BypassVpnService`: полный lifecycle (prepare → startForeground → establishTun)
- [x] Регистрация сервиса в манифесте (`android.permission.BIND_VPN_SERVICE`)
- [x] Переключатель в настройках; запрос разрешения через
      `startActivityForResult(REQ_VPN_PERMISSION = 7001)`
- [x] Строки интерфейса bypass

### Этап 2 — движок DPI-обхода (написан, не проверен на устройстве)

- [x] Разбор IPv4-заголовка, TCP и UDP (UDP релеится только порт 53;
      QUIC/прочий UDP дропается — браузер откатывается на TCP)
- [x] Выделение TCP-потоков по `(src, dst, ports)` + проверка dstIp,
      вахтёр на idle-потоки (30с/120с)
- [x] Mini-TCP к приложению: свой SYN+ACK с нашим ISN, сплайсинг seq/ack,
      ретрансмиты, FIN/RST, TFO-данные в SYN
- [x] Исходящие соединения через `Socket(protect())` — выходящие сокеты
      не заворачиваются обратно в TUN
- [x] SNI из TLS ClientHello (расширение `server_name`)
- [x] DPI-эвейжн в стиле zapret: первый ClientHello для доменов из
      `BLOCKED_SUFFIXES` (youtube.com, googlevideo.com, ytimg.com, google.com …)
      ломается на два сегмента с разрезом внутри имени SNI + пауза 7 мс
      (`TCP_NODELAY`) — DPI не видит SNI в первом сегменте
- [x] DNS: релей UDP:53 через `DatagramSocket(protect())` на исходный
      адрес (77.88.8.8 / 77.88.8.1 из TUN-конфигурации), ответ обратно в TUN
- [x] `isAvailable()` == true; allowlist пакетов в VPN
- [ ] Проверка на устройстве против реально заблокированных доменов

### Этап 3 — проверка и полировка

- [ ] Тест на устройстве против реально заблокированных доменов
- [ ] Если обход не сработал — фолбэк: не ронять остальной трафик устройства
- [ ] Повторное подключение при смене сети, расход батареи, скорость

---

## Сборка

Ветку собирает тот же `build.ps1`, что и `main`. Это уже полноценный вариант
обхода — включается переключателем «Обход блокировок (VPN)» в настройках.
